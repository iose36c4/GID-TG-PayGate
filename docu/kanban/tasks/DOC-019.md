# [[DOC-019]] ADR-008: Idempotencia y Eventos de Dominio

## Descripción
Documentar las decisiones de **idempotencia** (Idempotency-Key en operaciones repetibles) y **eventos de dominio persistidos** (event store ligero, no Event Sourcing completo) como mecanismos gemelos de consistencia y auditoría del núcleo transaccional.

## Código de Ejemplo
```markdown
# ADR-008: Idempotencia + Eventos de Dominio

## Status
Accepted

## Contexto
- Los webhooks de pasarela pueden repetirse; el retry de red es inevitable.
- Sin idempotencia un mismo pago puede cobrarse N veces (RSK-001).
- La auditoría requiere saber exactamente qué ocurrió y cuándo.

## Decisión
1. **Idempotencia**: operaciones mutables (crear pago, refund, retiro, confirmar webhook)
   requieren `Idempotency-Key`; el servidor reutiliza la respuesta original.
   - Refuerzo en DB: ledger `entry_group` UNIQUE y transacciones con `lockForUpdate`.
2. **Eventos de dominio**: cada transición emite eventos (`InvoiceCreated`,
   `PaymentSucceeded`, `RefundCompleted`, `WebhookReceived`, `WithdrawalApproved`...)
   persistidos en `domain_events` (inmutable) para auditoría y replay de listeners.
   - NO Event Sourcing completo: el estado vive en la DB normal.

## Consecuencias
- Positivas: sin doble cobro, trazabilidad E2E, reprocesamiento de efectos.
- Negativas: coste de guardar eventos y diseñar listeners idempotentes.

- [[SEC-018]] Event store ligero
```

## Notas Técnicas
- Distinguir idempotencia de aplicación (Idempotency-Key) de idempotencia de datos (entry_group UNIQUE)
- El evento store es fuente de auditoría, no de reconstrucción de estado

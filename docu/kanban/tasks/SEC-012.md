# [[SEC-012]] Máquina de Estados del Refund

## Descripción
Máquina de estados del **reembolso**: `Created → Requested | Approved → Processed | Failed | Rejected | Partial → Completed`. Un refund solo puede crearse sobre un payment `Paid` y debe postear asientos inversos en el ledger. Todo refund es auditado e idempotente.

## Código de Ejemplo
```php
enum RefundState: string
{
    case Created = 'created';
    case Requested = 'requested';
    case Approved = 'approved';
    case Processed = 'processed';
    case Partial = 'partial';
    case Completed = 'completed';
    case Failed = 'failed';
    case Rejected = 'rejected';

    public function allowedTransitions(): array
    {
        return match ($this) {
            self::Created => [self::Requested, self::Rejected],
            self::Requested => [self::Approved, self::Rejected, self::Failed],
            self::Approved => [self::Processed, self::Partial, self::Failed],
            self::Processed => [self::Completed],
            self::Partial => [self::Processed, self::Completed],
            default => [],
        };
    }
}
```

## Criterios de Aceptación
- [ ] Enum `RefundState` + transiciones validadas
- [ ] Regla de negocio: `refund.total <= payment.paid` y nunca supera saldo
- [ ] Asientos inversos posteados al ledger (`refund` debit contra `cash_platform`)
- [ ] Refund idempotente (mismo `Idempotency-Key` → misma respuesta)
- [ ] Refund parcial soportado (estado `Partial`)
- [ ] Eventos de dominio `RefundCreated`/`RefundCompleted` emitidos (SEC-017)

## Notas Técnicas
- Verificar contra la pasarela el resultado real; el estado `Processed` requiere confirmación del proveedor
- `Failed` reintenta vía pipeline (SEC-035); agotado → alerta manual staff
- Nunca permitir refund de un payment `Frozen` sin autorización staff (SEC-015)

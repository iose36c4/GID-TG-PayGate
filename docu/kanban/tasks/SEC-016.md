# [[SEC-016]] Idempotencia con Idempotency-Key

## Descripción
Implementar **idempotencia** en todas las operaciones que pueden repetirse: crear pago, confirmar webhook, ejecutar refund, disparar retiro. Cliente envía `Idempotency-Key`; el servidor reutiliza la respuesta original si la clave ya se usó. Previene **cobros duplicados** por retry/replay.

## Código de Ejemplo
```php
// app/Domains/Financiero/Services/IdempotencyService.php
final class IdempotencyService
{
    public function execute(string $key, Closure $operation, string $resourceType, string $resourceId): mixed
    {
        return DB::transaction(function () use ($key, $operation, $resourceType, $resourceId) {
            $existing = IdempotencyRecord::where('key', $key)->lockForUpdate()->first();

            if ($existing) {
                return $existing->response; // replay -> misma respuesta
            }

            $result = $operation();

            IdempotencyRecord::create([
                'key'            => $key,
                'resource_type'  => $resourceType,
                'resource_id'    => $resourceId,
                'response_hash'  => hash('sha256', serialize($result)),
                'response'       => $result,
            ]);

            return $result;
        });
    }
}

// Middleware de API para clientes
// Header: Idempotency-Key: <uuid> + Retry-After en conflictos
```

## Criterios de Aceptación
- [ ] Middleware `EnsureIdempotencyKey` para rutas marcadas
- [ ] Tabla `idempotency_records` con UNIQUE `key` y `lockForUpdate()` (ver SEC-020)
- [ ] Header `Idempotency-Key` obligatorio en: create payment, refund, withdrawal, webhook confirm
- [ ] Replay devuelve exactamente la respuesta original (200 con mismo payload)
- [ ] Clave expira según política (configurable, ej. 24h) con limpieza programada
- [ ] Tests de doble POST simultáneo (race) sin doble cobro (SEC-043)

## Cálculos y Algoritmos (LaTeX)
### Decisiones
$$
\text{Idempotency} = \{ \text{createPayment}, \text{confirmWebhook}, \text{executeRefund}, \text{requestWithdrawal} \}
$$

## Notas Técnicas
- Clave generada por cliente como UUID; servidor nunca la genera por el cliente
- No reutilizar claves para operaciones distintas
- Combinar con idempotencia natural del ledger (`entry_group`) como segunda barrera
- Almacenar hash de la respuesta para detección de anomalías
- Es control de mitigación de RSK-001 (doble cobro por replay)

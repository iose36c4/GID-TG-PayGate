# [[SEC-018]] Event Store Ligero + Reprocesamiento

## Descripción
Persistir el historial de eventos de dominio como **event store ligero** (tabla `domain_events` inmutable) para auditoría, análisis forense y **reprocesamiento** de listeners fallidos. No es Event Sourcing completo: el estado vive en la DB normal, pero los eventos quedan registrados y son reproducibles.

## Código de Ejemplo
```sql
CREATE TABLE domain_events (
  id             CHAR(36) PRIMARY KEY,
  type           VARCHAR(100) NOT NULL,   -- 'payment.succeeded'
  aggregate_type VARCHAR(60)  NOT NULL,   -- 'Payment'
  aggregate_id   CHAR(36)     NOT NULL,
  payload        JSON         NOT NULL,   -- diff/estado relevante
  actor_type     VARCHAR(20),             -- 'user'|'system'|'webhook'|'cron'
  actor_id       VARCHAR(40),
  correlation_id CHAR(36)     NOT NULL,
  created_at     TIMESTAMP(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  INDEX idx_evt_agg (aggregate_type, aggregate_id, created_at),
  INDEX idx_evt_corr (correlation_id)
);
```

```php
// Reprocesar listeners de un rango/agregado
Artisan::call('events:replay', ['--since' => '2026-08-01', '--type' => 'payment.succeeded']);
```

## Criterios de Aceptación
- [ ] Tabla `domain_events` inmutable (sin UPDATE/DELETE) con índices de búsqueda
- [ ] Todos los eventos SEC-017 persistidos con `correlation_id`
- [ ] Comando `events:replay` que re-ejecuta listeners (idempotente)
- [ ] Vista/UI de auditoría de eventos por agregado (staff/admin)
- [ ] Retención configurable (ej. 12 meses activo + archivo)
- [ ] Replay de prueba: generar entorno desde eventos == mismo estado final

## Notas Técnicas
- La inmutabilidad se protege en DB (trigger o permisos) y en el ORM (sin métodos de update)
- El payload NO debe contener datos sensibles en claro (solo referencias)
- El replay debe ser seguro: los listeners que escriben deben ser idempotentes
- Es la fuente de datos para las métricas de auditoría y compliance

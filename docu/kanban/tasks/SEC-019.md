# [[SEC-019]] Reconciliación Sistema ↔ Proveedor ↔ Banco ↔ Ledger

## Descripción
Implementar el proceso de **reconciliación** entre capas: transacciones del sistema ↔ reportes de la pasarela (Stripe/MP) ↔ extractos bancarios ↔ ledger. Detecta pagos huérfanos, montos distintos, cobros no esperados y errores de asiento. Job diario + dashboard de discrepancias.

## Código de Ejemplo
```php
final class ReconciliationService
{
    /** @return Discrepancy[] */
    public function reconcile(Carbon $date): array
    {
        $ledger = $this->aggregateDaily($date, 'cash_platform');
        $provider = $this->provider->fetchSettlements($date); // Stripe/MP

        return $this->match($ledger, $provider)->discrepancies([
            'orphan_provider_tx'   => $this->orphanProviderTransactions($provider),
            'orphan_ledger_tx'     => $this->orphanLedgerTransactions($ledger),
            'amount_mismatch'      => $this->amountMismatches($ledger, $provider),
            'missing_settlement'   => $this->missingSettlements($ledger),
        ]);
    }
}

// php artisan reconcile:run --date=2026-08-04  -> crea reporte + alerta si hay gaps
```

## Criterios de Aceptación
- [ ] Servicio de reconciliación multi-fuente con reglas de matching (reference_id, monto, moneda, fecha)
- [ ] Detección: orphan provider, orphan ledger, amount mismatch, settlement faltante
- [ ] Job diario `reconcile:run` con reporte y alerta ante discrepancias
- [ ] Dashboard staff/admin de discrepancias con resolución (marcar, ajustar, escalar)
- [ ] Ejecución manual bajo demanda para fechas históricas
- [ ] Regla: retiros/pagos detenidos si la reconciliación del día anterior falla (kill switch)

## Notas Técnicas
- El `reference_id` del ledger debe mapear al `id` de transacción del proveedor
- Las diferencias de timestamps (timezones, pagos diferidos) se manejan con ventana de ±24h
- Mantener el balance de `pending_settlement` para cuadrar días no cerrados
- Es un control directo de RSK-001 (pagos fantasma/dobles)

# [[SEC-020]] Concurrencia: SELECT FOR UPDATE + Optimistic Locking

## Descripción
Estrategia de **concurrencia** para operaciones de dinero: `SELECT ... FOR UPDATE` (pessimistic lock) para lecturas que luego escriben (cobro, retiro, refund) y `version` columns (optimistic lock) para entidades donde el conflicto es raro. Prevenir doble cobro, retiro duplicado y saldos negativos por carreras.

## Código de Ejemplo
```php
// Cargo de retiro: transacción + lock pesimista sobre el balance objetivo
DB::transaction(function () use ($withdrawal) {
    $balance = DB::table('accounts')
        ->where('code', 'payable_creator')
        ->where('currency', $withdrawal->currency->code)
        ->lockForUpdate()                    // bloquea carrera entre retiros
        ->first();

    $available = BalanceService::fromAccount($balance); // agregación + lock

    if ($available->amountInCents() < $withdrawal->amount->amountInCents()) {
        throw new InsufficientBalance(...);
    }

    $withdrawal->transitionTo(WithdrawalState::Approved);
    LedgerService::post($withdrawal->entryGroup(), $asientos);
});
```

```php
// Optimistic lock con columna version
$payment = Payment::where('id', $id)->where('version', $requestedVersion)->first();
if (!$payment) throw new OptimisticLockException();
$payment->transitionTo(PaymentState::Paid);
$payment->version++;
$payment->save(); // WHERE version = ? -> 0 filas afectadas = conflicto
```

## Criterios de Aceptación
- [ ] `lockForUpdate()` en: cargo de retiro, post de ledger por cuenta, transición de pago en confirmación webhook
- [ ] Columna `version` en entidades financieras (Payment, Invoice, Withdrawal, Balance materializado)
- [ ] Retry de conflictos con backoff exponencial + jitter
- [ ] Timeout de lock configurado (evitar deadlocks largos) con logging
- [ ] Tests de carrera concurrente (SEC-043): 10 threads, 1 retiro → solo 1 éxito

## Notas Técnicas
- Orden fijo de adquisición de locks para evitar deadlocks (ver SEC-021)
- El ledger (`entry_group` UNIQUE) es la barrera final de idempotencia
- Las transacciones de dinero deben ser cortas: no llamar HTTP dentro del lock
- InnoDB: usar transacciones con `isolation` por defecto y `lockForUpdate`

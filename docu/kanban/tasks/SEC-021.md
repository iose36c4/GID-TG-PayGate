# [[SEC-021]] Distributed Locks + Deadlock Retry + Updates Atómicos

## Descripción
Resolver **deadlocks** y coordinar operaciones distribuidas (workers, cron, webhooks concurrentes): orden fijo de locks, reintento automático ante `40001`/`1213` (deadlock), `atomic()` updates de Laravel, y locks distribuidos sobre Redis para jobs que no deben solaparse (reconciliación, expiración, cierre diario).

## Código de Ejemplo
```php
// Reintento de deadlock (MySQL error 1213)
DB::transaction(function () { ... }, 3); // Laravel retries por defecto 1

// Actualización atómica condicional
Payment::where('id', $id)
    ->where('state', PaymentState::WaitingConfirmation->value)
    ->update(['state' => PaymentState::Paid->value, 'version' => DB::raw('version + 1')]);

// Lock distribuido Redis para job de cierre diario
RedisLock::lock('reconcile:'.$date, 600)->get(function () {
    $this->reconcile($date); // solo un worker por fecha
});
```

## Criterios de Aceptación
- [ ] Orden de locks documentado (ej. cuenta → entidad → evento) y aplicado en todo el código de dinero
- [ ] Config de reintento de transacciones ante deadlock (3 intentos) en servicios de dominio
- [ ] Updates atómicos con `WHERE` de estado + `version` (no read-modify-write a ciegas)
- [ ] Locks distribuidos Redis en: reconcile, expiración de invoices, cierre de día, limpieza de tokens
- [ ] Timeouts y TTL de locks configurados con renovación segura
- [ ] Tests de deadlock inducido con resolución correcta

## Notas Técnicas
- Mantener las transacciones lo más cortas posibles (sin llamadas externas dentro)
- Redis lock vía `illuminate/cache` (Cache::lock) con TTL y owner token
- Si Redis no disponible, fallback a locks de DB con comportamiento degradado explícito
- Registrar cada deadlock resuelto para observar frecuencia (SEC-038)

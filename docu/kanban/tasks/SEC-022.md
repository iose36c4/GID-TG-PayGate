# [[SEC-022]] Arquitectura de Autorización (separada de Auth)

## Descripción
Definir la **arquitectura de autorización** como capa independiente de la autenticación: todo acceso a recurso pasa por una política o servicio de autorización, nunca solo por "está logueado". Reglas por rol, por propietario de recurso y por contexto (subdominio, feature flag, estado del recurso). Documentado en `docu/arquitectura/autorizacion.md`.

## Código de Ejemplo
```php
// app/Providers/AuthorizationServiceProvider.php
Gate::policy(Invoice::class, InvoicePolicy::class);
Gate::policy(Payment::class, PaymentPolicy::class);
Gate::policy(Withdrawal::class, WithdrawalPolicy::class);
Gate::policy(LedgerEntry::class, LedgerEntryPolicy::class);
Gate::policy(Dispute::class, DisputePolicy::class);

// Uso en servicios (no solo en controladores)
if (!Gate::allows('refund', $payment)) {
    throw new AuthorizationException('No autorizado para reembolsar');
}
```

## Criterios de Aceptación
- [ ] `autorizacion.md` con: principios, matriz de reglas, flujo de decisión, excepciones
- [ ] Toda entidad financiera tiene Policy registrada
- [ ] Servicios de dominio chequean autorización, no solo controladores
- [ ] Autorización denegada → 403 con logging de auditoría (SEC-036)
- [ ] Sin reglas `if ($user->role == 'admin')` sueltas en el código (centralizado)
- [ ] Principio de mínimo privilegio aplicado a todos los roles

## Notas Técnicas
- Separar: **autenticación** (¿quién es?) de **autorización** (¿puede hacerlo?)
- Combinar RBAC (SEC-024) + ABAC/tenant (SEC-025) de forma consistente
- Las Policies deben devolver `Response::deny()` con motivo para auditoría
- El subdominio no debe ser la única barrera: es UX, no control de seguridad

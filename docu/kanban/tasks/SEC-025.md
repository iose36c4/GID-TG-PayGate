# [[SEC-025]] ABAC + Tenant Scoping Creador→Recursos Propios

## Descripción
Implementar **ABAC** (Attribute-Based Access Control) para reglas que RBAC no expresa: "creador solo accede a sus propios pagos", "staff accede por jurisdicción/equipo", "estado del recurso condiciona la acción". Centralizar el scoping por tenancy (creador → canales → pagos) en servicios reutilizables y scopes de Eloquent.

## Código de Ejemplo
```php
// app/Domains/Financiero/Policies/TenantScope.php
final class TenantScope
{
    public function canAccess(User $user, Channel $channel): bool
    {
        if ($user->hasRole('admin')) return true;

        return $channel->owner_id === $user->id
            || $channel->collaborators()->where('user_id', $user->id)->exists();
    }

    public function query(Payment|Builder $builder, User $user): Builder
    {
        // FORZADO: nunca devuelve pagos de otros creadores
        if ($user->hasAnyRole(['staff', 'admin'])) return $builder;

        return $builder->whereHas('channel', fn (Builder $q) => $q
            ->where('owner_id', $user->id)
            ->orWhereHas('collaborators', fn (Builder $q2) => $q2->where('user_id', $user->id)));
    }
}
```

## Criterios de Aceptación
- [ ] Scopes de tenancy aplicados a: Channel, Payment, Subscription, Invoice, Withdrawal, Analytics
- [ ] Scope forzado a nivel de query (no solo filtrar en UI)
- [ ] Reglas condicionales por atributo: estado del recurso, jurisdicción, feature flag
- [ ] `canAccess` centralizado y usado por Policies + Services
- [ ] Tests: creador A no ve/opera recursos de creador B (IDOR) — vinculado a SEC-047
- [ ] Documentado en `autorizacion.md` (parte ABAC)

## Notas Técnicas
- El scope de tenancy es la defensa principal contra IDOR (SEC-047)
- Aplicar SIEMPRE, incluso cuando el usuario tiene el permiso global (menos privilegio)
- Cuidado con `orWhere` que rompe scopes globales: agrupar correctamente
- Para colaboradores usar tabla `channel_user` con rol del colaborador

# [[SEC-027]] Matriz de Acceso + Tests de Autorización

## Descripción
Construir la **matriz de acceso** completa (rol × recurso × acción → permitir/denegar) y los tests parametrizados que la verifiquen. Es el documento y la suite que prueban la arquitectura de autorización: nadie accede a recursos ajenos, staff/admin según reglas, y los cambios de permisos no rompen el modelo.

## Código de Ejemplo
```php
// tests/Feature/Security/AuthorizationMatrixTest.php
test('matriz de autorización', function (array $case) {
    ['role' => $role, 'actor' => $actor, 'resource' => $resource, 'action' => $action, 'expected' => $expected] = $case;

    $response = actingAsRole($actor, $role)->perform($action, $resource);

    $expected === 'allow'
        ? $response->assertOk()          // o 403 no
        : $response->assertForbidden();
})->with([
    // [rol, actor, recurso, acción, resultado]
    ['creador',  'owner',   'payment_own',   'refund',  'allow'],
    ['creador',  'other',   'payment_other', 'refund',  'deny'],
    ['creador',  'owner',   'payment_other', 'view',    'deny'],
    ['staff-finanzas', 'staff', 'payment_any', 'refund', 'allow'],
    ['user',     'customer','payment_own',   'view',    'allow'],
    ['user',     'customer','payment_other', 'view',    'deny'],
]);
```

## Criterios de Aceptación
- [ ] Matriz `docu/arquitectura/autorizacion/matriz.md` completa (roles × recursos × acciones)
- [ ] Test parametrizado con 30+ casos que cubren la matriz
- [ ] Casos clave IDOR: creador A vs recursos de creador B (view, refund, cancel)
- [ ] Cohorte de roles nuevos rompe tests si no se actualiza la matriz
- [ ] Corrida en CI obligatoria (bloquea merge)
- [ ] La matriz cubre: web, API (scopes) y servicios de dominio

## Notas Técnicas
- Usar data providers de Pest para cada caso
- Los tests de Policies se complementan con tests de API reales (feature)
- Actualizar la matriz cuando se agregue un permiso o rol nuevo
- Vincular como verificación de RSK-003 (IDOR)

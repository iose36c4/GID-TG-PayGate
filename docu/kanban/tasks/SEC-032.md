# [[SEC-032]] Telegram Flood Control + Rate Limit por Usuario + Expiración

## Descripción
Proteger el bot y los flujos de pago/invitación de Telegram contra **flood**: límites por usuario (comandos, intentos de pago, solicitudes de invite), cooldowns, expiración de comandos pendientes, y detección de comportamiento anómalo. Los comandos con valor económico expiran y se invalidan.

## Código de Ejemplo
```php
// Rate limit por (telegram_id, comando) con Redis
$key = "tg:rl:{$telegramId}:{$command}";
$remaining = RateLimiter::attempts($key);

if (!RateLimiter::tooManyAttempts($key, $limit, $decaySeconds)) {
    RateLimiter::hit($key, $decaySeconds);
} else {
    return response()->json(['error' => 'Demasiadas solicitudes'], 429);
}

// Expiración de comando de pago
// pay_order:{order_id}:{telegram_id} con TTL = 15 min
if (Cache::get($paymentIntentKey) === null) {
    return $this->replyExpired('El enlace de pago expiró. Genera uno nuevo.');
}
```

## Criterios de Aceptación
- [ ] Rate limits por usuario por comando: `/start` 10/5min, pago 5/hora, invite 3/hora
- [ ] Comandos de pago con expiración (TTL) → respuesta de "expired" clara
- [ ] Flood de updates (misma persona, muchos update_id) no satura colas
- [ ] Anomalías logueadas y estudiadas (velocidad, horarios) en SEC-036
- [ ] Límites configurables por canal/creador
- [ ] Tests: exceder límite → 429/cooldown; expiración → flujo rechazado

## Notas Técnicas
- Usar Redis (disponible en runtime) y fallback DB cuando no exista
- Los invite links de un canal con abuso se revocan y regeneran (PUB-008)
- El flood control aplica tanto al webhook de entrada como al envío saliente (429 de Telegram)
- Compartir técnica con SEC-033 (rate limiting transversal)

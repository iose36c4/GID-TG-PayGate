# [[SEC-040]] Secret Management: Rotación + Key Versioning

## Descripción
Gestión completa de **secretos**: tokens de bot Telegram (AES-256 en DB con cast), claves de pasarelas, secretos de firma, `APP_KEY` y credenciales de DB/Redis. Todo en variables de entorno (`.env`), nunca en el repo. Incluye: **rotación**, **key versioning** (cifrar con versión, verificar contra anterior), `crypto.key_rotation` y plan KMS-ready.

## Código de Ejemplo
```php
// app/Models/Casts/EncryptedToken.php (Laravel 11: el cast por defecto ya usa AES-256-CBC)
$channel->telegram_token; // -> string descifrado (nunca loguearlo)

// Key versioning
// config/app.php
'cipher_keys' => [
    'v1' => env('APP_KEY_V1'),   // vigente
    'v0' => env('APP_KEY_V0'),   // anterior (solo descifrar)
],

// Comando de rotación
php artisan crypto:rotate --from=v0 --to=v1
// 1) cifrar todos los campos con v1 manteniendo los índices de v0
// 2) verificar round-trip
// 3) eliminar v0

// Tokens de API (SEC-026): hash en DB + revocación
```

## Criterios de Aceptación
- [ ] Todos los secretos en env vars; `.env.example` con placeholders sin valores reales
- [ ] Tokens Telegram con cast de cifrado (Eloquent casts, AES-256)
- [ ] Sistema de `key_version` (cifrado → versión + datos) y comando de rotación
- [ ] Rotación de `APP_KEY` soportada sin perder datos cifrados
- [ ] Sin secretos en logs, repos, frontend ni respaldos (TST-S-003 lo verifica)
- [ ] Plan KMS-ready documentado (migrar claves maestras a KMS/HSM sin rediseñar)
- [ ] Revocación inmediata de cualquier secreto comprometido (runbook)

## Notas Técnicas
- PCI: no almacenar tarjetas; las claves de pasarela son tokens de API, se cifran igual
- Los secretos rotados se verifican en SEC-030 (webhook signature) y TST-S-009
- Para multi-cifrado: prefijo de versión en el valor cifrado (`v1$base64`)
- `crypto:rotate` debe ejecutarse con el sistema en modo mantenimiento y verificarse con SEC-010/019
- Es mitigación de RSK-002 (tokens Telegram filtrados)
